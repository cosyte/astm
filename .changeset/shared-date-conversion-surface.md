**`toObject`, `toISO` and `toDate`: the shared `@cosyte` date conversion surface, with the timezone honesty ASTM forces.** A parsed `AstmDate` could be rendered (`astmDateToLocalISO`) but not read as components and not converted to an instant, and the name it was rendered under was this package's alone, so a consumer holding dates from two `@cosyte` parsers wrote two different conversions for the same job. The three names, their return shapes and their timezone rule are now identical across the sibling parsers, so moving between them costs nothing to relearn.

Added:

- `toObject(value)`: a **frozen** object carrying only the components the value stated (`{ year: 2024, month: 3, day: 15 }` for `"20240315"`), with a spec-native 1-to-12 month and singular `hour`/`minute`/`second` keys. Nothing is zero-filled and no key holds `undefined`, so `Object.keys()` is the value's precision. The parse bookkeeping stays on `AstmDate` and does not cross over: there is no `raw`, `precision` or `truncated` key, and a digit run that cut a component in half reports only its complete components, with the dangling digit reaching no field. Deleting `offsetMinutes`, which an ASTM value never carries, leaves an object `Temporal.PlainDateTime.from` and luxon's `DateTime.fromObject` accept with no key rename and no value adjustment. Neither library is a dependency: the shape is the interoperability, not an import.
- `toISO(value)`: ISO-8601 truncated to the stated precision, never padded out to a precision the value did not state, and with no `Z` and no offset appended because ASTM states none. It returns the same string `astmDateToLocalISO` returns for every value `parseAstmDate` produces. That function is unchanged, still exported, and still the repo-native name.
- `toDate(value, options?)`: an absolute-instant `Date`, and **only** when the caller makes the zone determinate with `options.assumeOffsetMinutes` (signed minutes east of UTC, an explicit `0` meaning "read this value as UTC"). An ASTM timestamp is local to the instrument that wrote it and states no offset, so without that assumption there is no instant to give and the answer is `undefined`. The host machine's zone is never read and UTC is never assumed: either guess is silent and shifts a date by a day in every negative-offset zone. Components below the stated precision fill to their lowest legal value for the instant only, leaving the value's own precision untouched, and a four-digit year below 100 stays that year (`"00500101"` is the year 50, never 1950).
- The `DateParts` and `ToDateOptions` types, and a README section documenting all three together with the import-aliasing pattern the shared names force on a consumer using two `@cosyte` parsers in one file.

None of the three ever throws: `undefined`, `null`, a value `parseAstmDate` refused, and a value stating no component at all each answer `undefined` rather than a partial one. Nothing else moved: no existing export was removed, renamed or changed in behaviour, no runtime or development dependency of any kind was added, and the supported Node.js floor is unchanged.
