Refuse a `startFrameNumber` that cannot be written as a frame number, which used to go out as whatever byte the arithmetic truncated to and could cost a framed stream every one of its records.

A frame's number is a single ASCII digit, written as the ASCII `0` plus the number, and nothing checked the number. Measured on this package's own round trip, `-1` put a `/` in the frame-number position, and `NaN`, `Infinity` and `-Infinity` each put a `NUL` there in every frame of the stream, after which the decoder recognised no frame number at all, warned on every frame, and emitted none of the records: a four-record message in, nothing out. Values that truncated back onto a digit were quieter and no better, since `1.5` and `257` each produced the byte-for-byte stream a start of `1` produces, so the option accepted values it documented as invalid without saying so.

`composeAstmFrames`, and `serializeFramedAstm` through it, now throw an `AstmFrameEncodeError` with the new code `ASTM_FRAME_INVALID_START_FRAME_NUMBER`, a fourth member of `AstmFrameEncodeErrorCode`, unless the option is a whole number from `0` to `7`. That domain is what a frame can carry, the same modulo-8 sequence the decoder reads and rolls over. Clamping or taking a modulo was rejected: both pick a frame number you did not ask for, and the frame number is the decoder's only evidence that no frame was dropped. The message names the value received, which is your own option and not stream content. `composeAstmFrames` checks it before it reads a record, so on that entry point the refusal never depends on your data; `serializeFramedAstm` serializes every record first, so a record that cannot be serialized at all is refused before this check runs on that route.

The whole `0` to `7` range is still accepted, because a non-default start has a real use: composing one transfer across several calls. Continuing the sequence at the number after the last frame the previous call used gives bytes identical to composing the whole list in one call, rollover included. What a continuation is not is the start of a transfer. Read on its own, a stream starting anywhere but `1` opens on a sequence gap, so the decoder does not emit that first record. What `parseFramedAstm` does after that varies with the message shape: it may throw, under more than one code, and it may return a message one record short. The record layer never reports the loss, because it only ever sees the records that survived, so read `frameWarnings` rather than keying on an outcome. The documented-valid `0` has always behaved that way; it is now stated on the option rather than left to be discovered, and `1` remains the default.

This narrows a published package, in a small population: `1.5` and `257` used to produce a working stream, the byte-for-byte start-at-`1` one, and now throw. Every value it turns away was already outside what the option documented: a frame number, a whole number from `0` to `7`.

Two documentation links in the published type declarations also named symbols that do not exist, `QuirkTolerance` for `AstmQuirkTolerance` and `FIRST_FRAME_NUMBER`, which this package does not export, and one more was left unqualified where a member was meant. Every documentation link in the shipped declarations now names a symbol that is declared there.
